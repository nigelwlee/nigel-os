# Engineering Frameworks

Mental models and tools for technical decision-making. Reference when designing systems, evaluating architecture, or directing AI coding agents.

---

## Architecture & System Design

**Monolith-First, Extract Later.** The default architecture for any new product should be a single deployable unit — a monolith. Microservices introduce distributed systems complexity (network failures, eventual consistency, deployment orchestration, service discovery) that is pure overhead when you are still finding product-market fit. A well-structured monolith with clear internal module boundaries gives you all the development speed of a single codebase while preserving the option to extract services later when you have empirical evidence of where the boundaries should be. The mistake most builders make is pre-emptively splitting into services based on guesses about future scale. When directing an AI agent, explicitly prompt for a monolithic architecture with modular internal structure — separate concerns in code, not in infrastructure. Extract a service only when you have a concrete reason: a component needs to scale independently, a team boundary demands it, or a different technology is required for a specific workload. Use for: any new project; resisting the temptation to over-architect at the start; knowing when (and when not to) break a monolith apart.

**Separation of Concerns via Clear Interfaces.** Every system should be decomposed into components that each handle one responsibility, communicating through well-defined interfaces (APIs, function signatures, message contracts). The goal is not to eliminate coupling — components must interact to be useful — but to make the coupling explicit and narrow. When you review AI-generated code, look for whether you can understand what a module does without reading its internals. If changing one module requires changes in three others, the interfaces are too leaky. For a vibe coder, the practical application is in prompt design: when you ask an AI to build a feature, define the interface first (what goes in, what comes out, what side effects occur) and let the AI fill in the implementation. This constrains the AI's choices in productive ways and makes the output easier to review. Use for: structuring prompts for AI coding agents; reviewing code for maintainability; deciding how to decompose a feature into work units.

**API Design: REST as Default, GraphQL When Justified.** REST with JSON over HTTP is the right default for most APIs because it is simple, well-understood, cacheable, and supported by every tool and framework. Design resources around nouns (users, orders, invoices), use standard HTTP methods (GET, POST, PUT, DELETE), return appropriate status codes, and version your API from day one (even if it is just /v1/). GraphQL is justified when you have multiple client types (web, mobile, third-party) with significantly different data needs and you want to avoid maintaining multiple REST endpoints — but it introduces complexity in caching, authorisation at the field level, and query performance (the N+1 problem moves from the backend to the query layer). When prompting an AI to build an API, specify your resource model, pagination approach (cursor-based for large datasets, offset for simple cases), and error response format upfront. Use for: designing any API; choosing between REST and GraphQL; specifying API contracts before AI generates implementation code.

**Database Selection by Access Pattern.** The choice of database should be driven by how you read and write data, not by familiarity or popularity. PostgreSQL is an excellent default for most applications — it handles relational data, supports JSON for semi-structured data, has strong consistency guarantees, and scales vertically to surprising levels. Choose a document database (like MongoDB) only when your data is genuinely document-shaped and you do not need cross-document transactions. Choose Redis when you need sub-millisecond reads for cached or ephemeral data. Choose a time-series database (like TimescaleDB or InfluxDB) for metrics, events, or IoT data. Choose SQLite for local-first applications, embedded systems, or single-user tools — it is radically simpler than a client-server database and surprisingly powerful. The most common mistake is choosing based on hype cycles or AI training data defaults. When prompting an AI, state your access patterns explicitly: "reads are 100x more frequent than writes," "queries always filter by user_id and date range," "we need full-text search across these fields." Use for: choosing a database for a new project; reviewing whether an AI's database choice matches your actual requirements.

## Development Process

**Version Control as Communication.** Git is not just a backup system — it is a communication tool. Every commit message should explain why a change was made, not what was changed (the diff shows the what). Use conventional commit formats (feat:, fix:, refactor:) to make history scannable. Branch naming should be descriptive (feature/add-stripe-billing, fix/login-redirect-loop). For a solo builder working with AI agents, version control is especially critical because AI-generated changes can be large and unpredictable. Commit frequently so you can revert cleanly. Create a new branch before any significant AI coding session so you always have a known-good state to return to. Never let an AI agent commit directly to main — always use a branch, review the diff, and merge deliberately. Use for: structuring your Git workflow; setting up guardrails before AI coding sessions; maintaining a clean project history.

**The Testing Pyramid (Adapted for AI-Built Code).** The traditional testing pyramid has many unit tests at the base, fewer integration tests in the middle, and a small number of end-to-end tests at the top. For AI-built code, the pyramid should be inverted in emphasis: integration and end-to-end tests are more valuable because they verify behavior from the user's perspective and are resilient to implementation changes. Unit tests are still useful for complex business logic, but AI agents frequently generate code whose internal structure changes between sessions, breaking unit tests that are coupled to implementation details. Write integration tests that exercise your API endpoints with realistic data. Write end-to-end tests for critical user flows (signup, payment, core workflow). Use unit tests for pure functions with complex logic (calculations, transformations, validations). When prompting an AI to write tests, specify what behaviors to test, not what functions to test. Use for: deciding what to test; reviewing AI-generated test suites; allocating testing effort where it provides the most confidence.

**Code Review for AI Output.** Code review of AI-generated code requires a different approach than reviewing human code. With humans, you review for intent and style; with AI, you review for correctness and hidden assumptions. Develop a checklist: (1) Does the database schema match your data model? (2) Are there hardcoded values that should be configuration? (3) Is error handling present and meaningful, or just generic try/catch blocks that swallow errors? (4) Are there security anti-patterns (SQL injection, missing input validation, exposed secrets)? (5) Does the code handle edge cases (empty inputs, missing data, concurrent access)? (6) Are dependencies well-chosen and actively maintained, or obscure libraries the AI hallucinated? Read every line of AI-generated code the first time. Over time, as you build trust with specific patterns and prompts, you can focus review on the areas most likely to contain problems. Use for: reviewing any code generated by AI agents; building a personal review checklist; knowing where AI output is most likely to be wrong.

**CI/CD as a Safety Net.** Continuous Integration means every change is automatically tested when merged. Continuous Deployment means every passing change is automatically deployed to production. For a solo builder, you need at minimum: a CI pipeline that runs your tests on every push, a staging environment that mirrors production, and a deployment process that can be rolled back in under five minutes. GitHub Actions is the simplest starting point — it is free for public repos and generous for private ones. Your pipeline should lint the code, run tests, build the artifact, and deploy. Automate everything that you would otherwise forget to do manually. The most important CI/CD principle for a vibe coder: if your tests pass in CI but the feature is broken, your tests are wrong, not your CI. Fix the tests so they catch real problems. Use for: setting up automated pipelines; deciding what to automate; ensuring AI-generated code does not break existing functionality.

## Infrastructure & Deployment

**The 12-Factor App in Practice.** The 12-Factor methodology provides twelve principles for building applications that are easy to deploy, scale, and maintain. The factors most relevant to a solo builder are: (1) Codebase — one repo per app, deployed to multiple environments from the same code. (2) Config — store all environment-specific values (API keys, database URLs, feature flags) in environment variables, never in code. (3) Backing services — treat databases, caches, email services, and APIs as attached resources that can be swapped by changing a URL. (4) Disposability — your app should start fast and shut down gracefully; do not store state in memory or on the local filesystem. (5) Dev/prod parity — keep development, staging, and production as similar as possible to avoid "works on my machine" failures. (6) Logs — write logs to stdout and let the platform handle routing them to a log aggregation service. When you prompt an AI to build a backend, explicitly state these constraints. AI agents frequently violate factors 2 (hardcoding config), 4 (writing to local filesystem), and 5 (using SQLite in dev but PostgreSQL in prod). Use for: reviewing AI-generated backend code for production-readiness; setting up deployment pipelines; avoiding common deployment pitfalls.

**Containers as Deployment Units.** Docker containers package your application with all its dependencies into a single, reproducible artifact that runs identically everywhere. For a solo builder, containers solve the "it works on my machine" problem and make deployment to any cloud provider straightforward. Your Dockerfile should be multi-stage (build in one stage, run in a smaller stage), pin specific base image versions (not :latest), and not run as root. Docker Compose is sufficient for running multi-service applications locally (your app + database + cache). For production, deploy containers to a managed service (Railway, Fly.io, Google Cloud Run, AWS ECS) rather than managing your own Kubernetes cluster — Kubernetes is powerful but its operational overhead is unjustifiable for a solo operator. When prompting an AI to generate a Dockerfile, specify the base image, the target platform, and whether you need a multi-stage build. Use for: packaging applications for deployment; choosing a container hosting platform; reviewing AI-generated Dockerfiles.

**Serverless vs. Servers: Choose by Workload.** Serverless (AWS Lambda, Vercel Functions, Cloudflare Workers) eliminates server management entirely — you deploy functions that run on demand and scale automatically. This is ideal for workloads that are bursty (webhook handlers, cron jobs, event processing) or low-traffic (side projects, internal tools). The trade-offs are: cold starts add latency to the first request, execution time is limited (usually 10-30 seconds), you cannot hold state in memory between requests, and debugging is harder because you cannot SSH into a running instance. Traditional servers (or long-running containers) are better for workloads that need persistent connections (WebSockets, streaming), long-running processes (video encoding, large data processing), or consistent low-latency responses. Many products use a hybrid: serverless for API endpoints and event handlers, a persistent server for background jobs and WebSocket connections. Use for: choosing between serverless and traditional deployment; deciding architecture for specific features; understanding the constraints of serverless platforms.

**CDN and Edge Computing.** A Content Delivery Network caches your static assets (images, CSS, JavaScript) on servers distributed globally, so users load them from a nearby location instead of your origin server. Every production application should use a CDN for static assets — it is cheap, simple to set up (Cloudflare, Vercel, Netlify all handle this automatically), and dramatically improves perceived performance. Edge computing takes this further by running your application logic at the edge, close to users. Cloudflare Workers and Vercel Edge Functions execute in hundreds of locations worldwide with sub-millisecond cold starts. This is powerful for personalisation, A/B testing, authentication checks, and any logic where latency matters. The constraint is that edge runtimes have limited APIs (no filesystem, restricted Node.js APIs) and smaller memory/compute budgets. Use for: improving application performance; deciding where to run application logic; understanding the CDN/edge stack of modern deployment platforms.

## Security & Reliability

**Authentication and Authorisation Patterns.** Authentication (who are you?) and authorisation (what can you do?) are the two most critical security concerns and the area where AI-generated code is most likely to contain subtle, dangerous bugs. Never implement your own authentication from scratch — use established services (Auth0, Clerk, Supabase Auth, Firebase Auth) or well-maintained libraries (NextAuth.js, Passport.js). For authorisation, implement role-based access control (RBAC) as your starting point: users have roles, roles have permissions, and every API endpoint checks permissions before executing. Store sessions in server-side stores (database or Redis), not in JWTs alone — JWTs cannot be revoked once issued unless you maintain a blacklist, which defeats their stateless advantage. Always hash passwords with bcrypt or argon2, never MD5 or SHA. Always use HTTPS. Always validate and sanitise all user input on the server, regardless of client-side validation. When reviewing AI-generated auth code, treat it as hostile until proven correct — the cost of a subtle auth bug is orders of magnitude higher than any other bug. Use for: choosing auth providers; reviewing AI-generated auth code; designing permission systems.

**SRE Error Budgets and SLOs.** A Service Level Objective (SLO) is a target for how reliable your service should be, expressed as a percentage (e.g., 99.9% of requests succeed within 500ms). An error budget is the inverse — the amount of unreliability you can tolerate (0.1%, or about 43 minutes of downtime per month). This framework transforms reliability from a vague aspiration into a concrete resource you can spend. When your error budget is healthy, ship features aggressively — some failures are acceptable. When your budget is depleted, stop shipping and fix reliability. For a solo builder, start with modest SLOs (99.5% availability is generous for early products) and tighten them as your user base grows and expectations increase. Monitor your SLOs with simple tooling: an uptime monitor (Better Uptime, UptimeRobot), error tracking (Sentry), and basic request latency metrics. You do not need a full observability stack on day one. Use for: deciding how much to invest in reliability; setting expectations with users; knowing when to prioritise stability over features.

**Backup Strategy: 3-2-1 Rule.** The 3-2-1 backup rule states: keep three copies of your data, on two different types of media, with one copy offsite. For a modern web application, this translates to: your primary database, an automated daily backup to a different storage service (e.g., S3), and a tested restore process. The most common failure mode is not losing backups — it is having backups that cannot actually be restored. Schedule a quarterly "fire drill" where you restore from backup to a fresh environment and verify the data is intact and the application works. Managed database services (Supabase, PlanetScale, RDS) handle automated backups for you, but you should still verify that point-in-time recovery works and understand the retention window. For critical data, also consider logical backups (pg_dump) in addition to physical snapshots, because logical backups are portable across database versions and cloud providers. Use for: setting up backup systems for production databases; verifying backup integrity; disaster recovery planning.

**OWASP Top 10 Awareness.** The Open Web Application Security Project maintains a list of the ten most critical web application security risks, updated periodically. As a vibe coder, you do not need to memorise the full list, but you need to know the top threats and verify that AI-generated code addresses them: (1) Broken Access Control — users can access resources they should not; always check permissions server-side. (2) Injection — SQL injection, XSS, and command injection; always use parameterised queries and sanitise output. (3) Insecure Design — security flaws baked into the architecture, not just the implementation; think about threat modelling before building. (4) Security Misconfiguration — default credentials, unnecessary features enabled, verbose error messages in production; audit your deployment settings. (5) Vulnerable Components — using libraries with known security vulnerabilities; run `npm audit` or equivalent regularly. When prompting an AI to build any user-facing feature, include "follow OWASP security best practices" in your prompt — it meaningfully improves the output. But do not rely on the AI's self-assessment of security; always review auth, data access, and input handling yourself. Use for: reviewing AI-generated code for security vulnerabilities; building a security-aware prompting habit; knowing which security concerns are most critical.

## Technical Decision-Making

**Build vs. Buy (and When to Use a Managed Service).** The default answer for a solo builder should be "buy" (or more precisely, "use a managed service") for anything that is not your core product differentiator. Auth? Use a service. Email? Use a service. Payments? Stripe. Database? Managed hosting. File storage? S3 or equivalent. Building these from scratch is a trap that feels productive but consumes time you should be spending on what makes your product unique. The exceptions are: when the managed service is too expensive at your scale, when it introduces unacceptable vendor lock-in for a critical component, or when your requirements are so unusual that no service fits. Even then, consider open-source self-hosted options before building custom. When evaluating a service, check: pricing at 10x your current scale, data export options (can you leave?), API quality and documentation, and the company's track record of reliability. Use for: any "should we build this?" decision; evaluating SaaS tools and infrastructure services; avoiding the trap of rebuilding solved problems.

**Technical Debt as a Conscious Choice.** Technical debt is not inherently bad — it is a deliberate trade-off of future development speed for present shipping speed. Like financial debt, the problem is not borrowing; it is borrowing without awareness or a repayment plan. When you prompt an AI to "just make it work," you are taking on technical debt. This is fine for prototypes, experiments, and time-sensitive launches. It becomes toxic when you forget the debt exists and build more features on top of it. Maintain a simple log of known technical debt: what shortcut was taken, why, and what the eventual fix looks like. Review this list before starting any major feature — sometimes paying down debt first makes the new feature dramatically easier to build. For AI-generated codebases specifically, debt accumulates in invisible ways: inconsistent patterns across files (because each was generated in a different session), duplicated logic (because the AI did not know about existing utilities), and over-complicated solutions (because the AI optimised for a general case you do not have). Use for: deciding when to cut corners consciously; maintaining a tech debt register; knowing when accumulated debt is blocking progress.

**Reversible vs. Irreversible Decisions.** Jeff Bezos distinguishes between Type 1 decisions (irreversible, high-consequence — walk through a one-way door) and Type 2 decisions (reversible, low-consequence — walk through a two-way door). Most technical decisions are Type 2 and should be made quickly: choosing a UI framework, picking a folder structure, selecting a CSS approach, naming conventions. A few are Type 1 and deserve careful deliberation: choosing a primary database, defining your core data model, selecting an authentication provider, choosing between a monolith and microservices, making commitments to external API contracts that others depend on. The failure mode for solo builders is treating every decision as Type 1 — agonising over framework choices that can be changed in a weekend — while accidentally treating Type 1 decisions as Type 2 (casually letting an AI choose your database schema without review). Develop the habit of classifying decisions before making them. For Type 2, set a five-minute time limit and move on. For Type 1, write an ADR and sleep on it. Use for: triaging technical decisions by importance; avoiding analysis paralysis on low-stakes choices; identifying which decisions deserve deep review.

**Architecture Decision Records (ADRs).** An ADR is a short document that captures a significant technical decision: the context (what problem are we solving?), the decision (what did we choose?), the alternatives considered (what else could we have done?), and the consequences (what trade-offs does this introduce?). ADRs are stored in version control alongside the code they describe. For a vibe coder, ADRs serve a dual purpose: they force you to think through a decision before implementing it, and they provide context for future AI coding sessions. When you return to a codebase after weeks away and prompt an AI to make changes, the ADRs tell both you and the AI why things are built the way they are. A minimal ADR is four paragraphs — context, decision, alternatives, consequences — stored in a /decisions folder in your repo. You do not need a template or a tool; a markdown file is sufficient. The discipline is in writing them consistently for every decision that would be hard to reverse. Use for: documenting significant technical choices; providing context for future AI coding sessions; forcing rigorous thinking before committing to architectural decisions.
